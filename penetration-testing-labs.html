CASE STUDY 01WINDOWS / IIS

Windows target: IIS & token impersonation

Assessed how anonymous file-transfer access and a web-root mapping could expose an IIS host to remote code execution and service-account privilege risks.

Anonymous FTP access → web-root file upload → IIS application context → token-privilege assessment

Defensive lessons

  • Separate upload locations from executable web roots.
  • Disable anonymous FTP and apply strict ACLs.
  • Remove unnecessary impersonation privileges and disable unneeded services.

CASE STUDY 02LINUX / APACHE

Linux host: file transfer, web access & sudo controls

Investigated a Linux application host with a non-standard file-transfer service, an exposed web path, and a privileged backup workflow with unsafe directory permissions.

High-port service discovery → web-service foothold → local permission review → sudo-policy impact

Defensive lessons

  • Audit high-numbered services; obscurity is not a control.
  • Restrict write access to privileged script directories.
  • Do not grant passwordless sudo for mutable application scripts.

CASE STUDY 03LEGACY LINUX

Legacy host: exposed shares & patch-management risk

Documented the compounding risk of unrestricted NFS exports, an internet-facing legacy CGI component, and an obsolete Linux kernel in a controlled legacy environment.

NFS share discovery → legacy web-component exposure → local kernel-risk validation → root-impact assessment

Defensive lessons

  • Patch legacy application and kernel components promptly.
  • Restrict NFS exports to trusted hosts and enforce root squashing.
  • Retire unsupported infrastructure wherever possible.

CASE STUDY 04MULTI-STAGE LINUX

Multi-stage Linux infrastructure assessment

Explored how several individually weak controls—exposed keys, weak credential storage, internal management access, and insecure automation—could be chained across a multi-user Linux host.

Exposed network share → credential exposure → internal-service access → multi-stage privilege analysis

Defensive lessons

  • Keep SSH keys and credential stores out of shared network paths.
  • Isolate management interfaces and enforce strong authentication.
  • Harden cron jobs, sudo rules, and internal application inputs.
